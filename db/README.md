> Deployment note: PostgreSQL remains local. Global Explorer ships its checked-in POWER cache and does not connect to this database on Vercel. AppEEARS/NDVI is disabled; archival NDVI imports require an explicit `--ndvi` path.

# Local PostgreSQL foundation

This milestone stores validated POWER and NDVI monthly observations. It does not introduce a database requirement for the website: current pages continue to load their existing sources and published snapshots. Background NASA workers and database-to-cache publication are subsequent milestones. No production database, cloud account or new web credential is needed for local development.

## Start locally on Windows

Docker Desktop must be installed and its Linux engine running. From the repository root:

```powershell
# Optional: start the installed engine if it is stopped.
docker desktop start

# Creates ignored db/.env with a random password if missing, then starts PostgreSQL.
./db/setup.ps1

# Use the existing project virtual environment, or create one first:
# python -m venv pipeline/.venv
./pipeline/.venv/Scripts/python.exe -m pip install -r pipeline/requirements-db.txt
./pipeline/.venv/Scripts/python.exe pipeline/database.py migrate
./pipeline/.venv/Scripts/python.exe pipeline/database.py import-validated --dry-run
./pipeline/.venv/Scripts/python.exe pipeline/database.py import-validated
./pipeline/.venv/Scripts/python.exe pipeline/database.py status
```

Database setup needs only `requirements-db.txt`, which includes the PostgreSQL driver and the same jsonschema version as the existing pipeline. It does not install notebooks or plotting packages. `requirements-trend.txt` remains the separate NumPy/SciPy reference environment. The browser has no new package dependency.

PostgreSQL 17.12 listens only on `127.0.0.1:54329` by default, avoiding the usual local port 5432. Data persists in the Compose named volume `earth-trend-detective_earth_postgres`. `db/.env` is Git-ignored and contains only local PostgreSQL settings. The loader reads it from the repository root regardless of working directory. Shell PG settings take precedence; `DATABASE_URL`, when supplied in the shell, overrides the local settings. Never prefix database credentials with `VITE_`, print a connection URI, or place passwords in command arguments.

For another OS, create `db/.env` from `.env.example`, replace its local password, then run:

```bash
docker compose --env-file db/.env up -d --wait db
pipeline/.venv/bin/python pipeline/database.py migrate
pipeline/.venv/bin/python pipeline/database.py import-validated
```

To stop the local service without removing data, run `docker compose --env-file db/.env stop db`. Starting it again preserves the volume. Do not delete the volume to rerun migrations or imports. Changing PGPASSWORD in an existing configuration does not rotate the password already initialized inside the volume; use PostgreSQL administration for a deliberate password change.

## Import scope and recovery

The importer defaults to the five saved live POWER responses under ignored `pipeline/raw/global-validation/` and the committed `pipeline/fixtures/ndvi-pilot.json`. It does not contact NASA and does not import synthetic featured-story datasets. Missing POWER snapshots fail explicitly; a fresh checkout needs original validated snapshots copied into that directory or generated by `npm run validate:global:live` in `web/`. Custom paths are supported with `--power-dir` and `--ndvi`.

All input files are normalized and validated before database writes. Each source artifact then commits in one transaction. On a failed artifact, neither its batch nor any observations remain. Completed artifacts survive subsequent failures, and rerunning the command skips identical completed imports. Import reports are stored in ignored `pipeline/raw/database-import-report.json` by default. A copied artifact has the same identity even if its local filename changes. A changed normalized payload under the same artifact/QA/normalizer identity is rejected instead of overwritten.

The first real import contains 195 location definitions, five POWER-capital artifacts with four variables each, and one Bangkok NDVI artifact: 6,048 monthly calendar positions. Of those, 5,764 are valid, 283 rejected and one missing. This is not a claim of observations at all 195 capitals. Reimporting the same six inputs adds zero records. See `docs/database-validation.json` for the measured local result.

## Shared observation contract

`contracts/observations.schema.json` is the versioned source-neutral monthly batch format. `contracts/observation-profiles.json` defines canonical units, source bounds, temporal meaning and annual aggregation for both sources. `pipeline/src/observations.py` normalizes original POWER response envelopes and already-validated NDVI snapshots into that contract.

An observation has a coordinate-specific location ID, variable, calendar month, canonical unit, value, quality and reason. Valid observations have a finite in-range numeric value and no rejection reason. Missing/rejected observations have a null value and a reason. Every location/variable record retains all 288 positions for 2001–2024. Zero and negative values within the source's range are retained. No interpolation or annual aggregation occurs during import.

POWER precipitation stays a monthly mean daily rate in mm/day. Solar radiation stays a mean daily energy value. Temperature and humidity remain monthly means. NDVI remains a unitless monthly composite, already scaled by AppEEARS, with its current strict QA exclusions preserved. Its snapshot has no raw rejected NDVI values or raw QA bits: these remain in the original ignored AppEEARS CSV, not invented in the database. Source-specific annual calculations remain described in the profiles and performed by existing application code until the cache-publishing milestone.

Each batch identifies the product/version, QA policy, normalizer version, source artifact checksum/path and original retrieval timestamp. POWER's version identifies the API version reported by NASA; it is not a claim to know an unreported underlying science-product revision. Source headers retained in the original artifact supply the remaining provenance. `artifact_path` is a local filesystem reference; durable object storage/upload is not implemented in this milestone.

## Tables and migrations

All tables live in the dedicated `earth` schema:

- `locations`: the 195 capital catalog, with coordinate-specific identities. A coordinate change produces a new identity.
- `products` and `product_variables`: source/version identity, canonical units, bounds, temporal meaning and aggregation rule.
- `ingestion_batches`: completed, checksum-addressed import revisions and provenance.
- `observations`: monthly validated/missing/rejected records. Constraints enforce month boundaries, units, quality/value consistency, finite values and source-specific ranges.
- `latest_observations`: newest retrieved revision per location, variable, product/version, QA policy and normalization version. Older data imported later does not replace newer retrieved data. Different source/QA/version streams remain distinct.
- `ingestion_jobs`: unique work identities, external task IDs, statuses, attempts, lease/checkpoint fields and retry timing. The resumable worker uses fenced leases and bounded retries; see [background ingestion](../docs/background-ingestion.md).
- `cache_releases`: prepared and published cache manifests, preserving release history.
- `schema_migrations`: applied filenames and SHA-256 checksums.

The migration runner locks migration application and applies pending SQL transactionally. Running it repeatedly is safe. Never edit an applied migration: the checksum check rejects it. Add the next numbered SQL file for future changes. There is no destructive rollback/reset command. Application imports preserve revisions; administrators can still change tables manually, so operational access should remain private.

## Verification

Default Python tests include offline observation-contract checks and skip real PostgreSQL tests unless explicitly enabled. To run against local PostgreSQL:

```powershell
$env:RUN_DATABASE_TESTS='1'
./pipeline/.venv/Scripts/python.exe -m pytest pipeline/tests -q
```

Install `pytest==8.3.4` to run the database/contract tests in a new database-only virtual environment. The full scientific test suite also needs the existing pipeline and trend requirements.

Integration tests create and remove only uniquely named `earth_test_<uuid>` databases. They never reset the project database. The configured role needs CREATE DATABASE for those tests; production ingestion roles need not have that permission. Tests cover repeatable/checksummed migrations, idempotent imports, changed-payload refusal, transaction rollback, revision ordering, units, bounds and month constraints. CI runs these checks against a separate PostgreSQL service.

The next milestone is resumable NASA ingestion workers plus versioned cache publication. The website should then consume generated files, with database ingestion credentials staying in background processes.

Measured local verification on November 15, 2026: 49 Python tests (including 8 real PostgreSQL integration cases), 133 web tests, production build and dataset checks passed. Browser checks confirmed Global Explorer POWER/NDVI, Workbench, Experience, Methods, Game and admin routes still render without a Vite error overlay. The local PostgreSQL service was left running for development.
